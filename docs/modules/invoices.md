# Invoices module

Core module (`includes/Modules/Invoices/`, locked: always active, cannot be deactivated). It numbers, renders, archives and e-mails PDF invoices for WooCommerce orders (lot 2), imports the 1.x data and serves the customer downloads (lot 3), and since 2.1 issues a credit note for every refund and gives the customers their documents in My Account, on the thank-you page and in the e-mails (lot 4a). VAT (no-VAT mode, customer VAT number, Factur-X) comes in 2.2.

Credit notes and customer access live in this module, not in the `CreditNotes` and `CustomerAccess` modules the v2 spec planned: they share the register, the pipeline, the settings form and the locked state, and a credit note module that could be deactivated would leave refunds of invoiced orders without their credit note.

## Architecture

One responsibility per folder under `includes/Modules/Invoices/`:

| Folder | Role |
|---|---|
| `Database/Installer` | Creates and upgrades the two tables (`lumia_factures_sequences`, `lumia_factures_documents`) with `dbDelta`, versioned in an option. |
| `Numbering/` | `Sequences` (atomic counters, one row per sequence key), `NumberFormat` (format tags, reset policy validation, preview). |
| `Documents/` | `Register` (the documents table: one row per order and type), `Issuer` (the invoice flow: gate, order meta, notes, hook), `CreditNoteIssuer` (the credit note of a refund), `InvoiceCancellation` (cancels the invoice of an unpaid order by a refund that moves no money), `Pipeline` (reserve, number, archive: the issuing core shared by every document type), `Notes` (the order note texts of one type), `IssuedDocument` (value object). |
| `Amounts/` | `StatementBuilder` turns an order into lines and total rows in integer cents (`Money`, `Line`, `TotalRow`, `Statement`); `CreditNoteStatementBuilder` does the same for a refund, read against its order (positive amounts, VAT rates of the order, a signed `adjustment` row for what the refund holds beyond its items); `Lines` holds the item readers both share. |
| `Rendering/` | `Context` (data for the templates), `Placeholders`, `Renderer` (HTML), `PdfEngine` (Dompdf), `Images` (logo), `Styles`. Templates live in `templates/pdf/`. |
| `Storage/Archive` | Write-once PDF files under `uploads/lumia-factures/Y/m/`. |
| `Emails/` | `Attachments` attaches the archived PDF to the WooCommerce e-mails chosen in the settings; `EmailLinks` prints the document links in the customer e-mails; `EmailIds` gives the canonical id of an e-mail (the refund e-mail renamed for a partial refund). |
| `Settings/` | `Schema`: single definition of the settings (defaults, sanitizing, bounds); `Upgrader`: one-time upgrade of the stored settings (2.1: the customer page links off on an existing site). |
| `Admin/` | Settings screen helpers (`Fields`, `Counters`, `Themes`), order screen (`OrderTools`), `Download`, live `Preview` and its `DemoOrder`, the notices `MigrationNotice` and `CreditNoteNotice`. |
| `Front/` | Customer side: `CustomerDownload` (endpoint and access check), `DocumentList` (the read-only list every customer surface prints), `Availability`, `CustomerLinks` (My Account and order pages), `Shortcode`, `OrderContext`. |
| `Migration/`, `Cli/` | The 1.x import and its issuing gate; the `wp lumia-factures` commands. |

Data flows one way: `Issuer` -> `Pipeline` -> `Register` / `Sequences` (numbers) -> `Renderer` (HTML from `Context` + `StatementBuilder`) -> `PdfEngine` (bytes) -> `Archive` (file) -> `Register::attach_file()`.

- Numbering is continuous and unique per document type. - The amounts on the PDF add up exactly to the WooCommerce total. `StatementTest::test_rounding_row_absorbs_real_drift`, `StatementTest::test_incl_discount_is_the_balancing_figure_without_rounding_row`, `StatementTest::test_zero_total_order`, `RenderingTest::test_summed_rows_always_print_and_toggles_hide_only_outside_the_sum`, `StatementTest::test_incl_discount_gap_above_rounding_keeps_woocommerce_discount`, `StatementTest::test_incl_balanced_discount_is_never_zero_or_positive`, `StatementTest::test_negative_fee_adds_up`, `StatementTest::test_taxed_shipping_incl_display`. For a credit note, the rows add up to the refunded amount: every `CreditNoteStatementTest` case checks the total row, the summed rows and the refund amount in both display modes (`assertAddsUp()`).
- No upgrade may lose an issued invoice or change its number. `DatabaseTest::test_install_is_idempotent`, `DatabaseTest::test_maybe_upgrade_does_nothing_when_up_to_date`, `DatabaseTest::test_upgrade_from_v1_keeps_issued_rows` (schema v2, see [core.md](../core.md#database-schema)); `uninstall.php` deletes nothing without the constant (its meta purge is covered by `UninstallerTest`).
- PHP >= 8.1 (tested on 8.3 and 8.5), WP >= 6.9, WooCommerce >= 9.0; HPOS and legacy storage: the whole suite runs on both (`npm test`, `npm run test:legacy`; `StorageModeTest`).

## Pitfalls

What broke (or would have), and why the solution is the one in the code.

- **C1: `$wpdb->insert_id` after an UPDATE.** 1.x read `insert_id` after an `UPDATE` to get the new counter. An `UPDATE` does not set it, so two invoices could share a number. `Sequences::next()` runs one atomic `UPDATE ... SET current_value = LAST_INSERT_ID(current_value + 1)` and reads `SELECT LAST_INSERT_ID()` (per connection). The number is never computed in PHP from a `SELECT`. Pinned by `SequencesTest::test_next_reads_value_not_insert_id`.
- **C2: the stale `WC_Order`.** The status hook hands over an order object loaded before the number meta exists; rendering from it printed invoices without their number. `Issuer` saves the meta, then renders from a fresh `wc_get_order()`. Pinned by `IssuerTest::test_rendered_pdf_contains_number`.
- **`get_formatted_meta_data( '_', $hide )`.** The first argument hides meta keys starting with `_`; the second (`$include_all`) must be the parent-name flag: with the parent name printed, the attributes already in the variation name would disappear; without it WooCommerce hides them so they are not printed twice (`StatementBuilder`). For a deleted product WooCommerce cannot map the attribute slug to its label, so the slug is humanised.
- **Atomicity without transactions.** The WordPress test suite wraps each test in a transaction; `START TRANSACTION` in the code would commit it and leak data between tests. Atomicity comes from the unique key on the documents table (one row per order and type: `Register::reserve()` is the lock), the single-statement counter update and guarded updates (`assign()` only updates a `reserved` row, `attach_file()` only fills an empty file, `release_stale()` only deletes an unnumbered row).
- **Temporary tables in tests.** Inside a test case `CREATE TABLE` becomes `CREATE TEMPORARY TABLE`, which the next connection cannot see. `tests/bootstrap.php` therefore runs `Installer::install()` on `setup_theme`, before the first test, so the real tables exist.
- **The `rounding` row.** WooCommerce rounds per line and per tax rate, so the printed rows can drift from the order total by a few cents. `StatementBuilder` appends a `rounding` row for the difference instead of absorbing it into another row, so the sum is always exact. Exception (incl. VAT display): a coupon split over two rates reads 4.99 once re-added, and the customer was really given 5.00, so the discount becomes the balancing figure (`balance_discount()`, gap of at most 5 minor units) and no rounding row remains.
- **A refund's tax items carry the rate of the refund day.** `wc_create_refund()` calls `update_taxes()`, which stamps each refund tax item with the shop rate as it is that day (percent and label), or with nothing once the rate is deleted. A credit note must print the VAT that was invoiced, so `CreditNoteStatementBuilder` keys every amount by rate id and reads the percent and label from the **order's** tax items (`Lines::rates()`), never from the refund's. In tests, WooCommerce serves rate rows from a per-request cache (`TaxRateDataStore`), so a rate changed mid-test does not reach the refund: `CreditNoteStatementTest::test_rate_taken_from_parent_after_tax_rate_changed_or_deleted` writes the day's rate on the refund tax items itself.
- **A line refund records a tax item at 0 for the rates it does not carry.** The order screen has one `refund_line_tax` input per order rate on every row and posts them all, 0 for a rate the row does not carry. Since WooCommerce 11.x, `WC_AJAX::refund_line_items()` and `wc_create_refund()` keep that 0 (`array_filter( ..., 'is_numeric' )`, so a real 0 % rate is not lost), and `update_taxes()` gives the refund a tax item at 0 for each such rate: a 20 % line refunded on a 20 % + 5.5 % order printed "VAT 5,5 % 0,00" on the credit note. `CreditNoteStatementBuilder::refunded_taxes()` drops a refund tax item at 0 unless the order rate is a real 0 % rate, which prints as on the invoice. The tests went through `OrderFactory::refund_line()`, which only sent the item's own rates and missed it: it now posts every order rate like the screen. Pinned by `CreditNoteStatementTest::test_line_refund_on_two_rate_order_shows_only_the_refunded_rate` and `test_real_zero_rate_keeps_its_row_as_on_the_invoice`.
- **The archive is never deleted.** PDFs are the legal record (10 years). No code path deletes a file: `Archive::store()` opens with `xb` (write-once), a rebuilt PDF is a **new** file, the damaged one stays, and uninstall never removes `uploads/lumia-factures/`, even with `LUMIA_FACTURES_REMOVE_ALL_DATA`.
- **The Nginx rule.** `.htaccess` protects Apache and LiteSpeed only; on Nginx the archive is public unless the server block contains `location ^~ /wp-content/uploads/lumia-factures/ { deny all; }` (README). File names carry 16 random hex characters as a second barrier.
- **Dompdf font cache.** Dompdf writes its font metrics under `uploads/lumia-factures/fonts/`, created with the same guards as the archive root before the first render (`Archive::ensure_root()`). `Archive::path()` refuses anything outside `Y/m/*.pdf`, so the cache is never served as an invoice.
- **HPOS order meta on uninstall.** `delete_post_meta_by_key()` only reaches `wp_postmeta`; `Core\Uninstaller::delete_order_meta()` also purges `{prefix}wc_orders_meta`.
- **A reset policy change moves to another counter (R38).** `reset_enabled` / `reset_period` choose the counter key (`invoice`, `invoice_2026`, `invoice_2026_10`). Switching (yearly to none, monthly to yearly, none to yearly) moved to a key starting at the start number, behind the issued numbers: every `assign()` failed on the duplicate, each order got a "skipped" note and no invoice. `Module::save_settings()` now raises the key the new policy uses for the current period to the current value of the old policy's key (`carry_counter()`, never lowers, logged) whenever the format or the policy changes. Safety net in `Pipeline::number()`: when `assign()` fails and `Register::number_exists()` proves the number is already issued, the next value is taken (20 attempts at most) without a note, since the skipped number is printed on another invoice and the series keeps no gap; any other `assign()` failure still burns the value with a note. Pinned by `IssuerTest::test_switch_*_continues_the_series`, `test_number_already_issued_is_skipped_without_note`, `test_number_retry_is_bounded`.
- **The PDF follows the user's language (R39).** Admin screens run in the user's locale (`determine_locale()`), so an admin with an English profile archived English invoices for good. `Renderer::html()` and `Renderer::pdf()` run inside `Renderer::in_site_locale()`: `switch_to_locale( get_locale() )` then `restore_previous_locale()` in a `finally`, only when the switch happened (it returns false when the request already runs in the site locale, and a restore without a switch would pop someone else's). The switch reloads every loaded text domain, the plugin's included, and `get_translations_for_domain()` loads it just in time from the path `load_plugin_textdomain()` registered, so no explicit reload is needed. `switch_to_locale()` refuses a locale whose core files are not installed. `LocaleTest` makes fr_FR available to the switcher by reflection (wp-env has no core language files) and relies on the plugin's own `.mo`.
- **Rebuild only what was never built (R41).** E-mails and downloads used to rebuild a missing or damaged archive on the fly, silently replacing the legal record with a PDF of today's order data. Now only an archive never built (register `file` IS NULL: render or storage failed at issue time) is built automatically. A recorded file that is missing or altered is never attached (logged) and never served: the 404 points to the explicit "Rebuild missing PDF" button of the order's invoice box, which still calls `Issuer::restore()`.
- **Free texts and `{current_date}`.** A rebuilt PDF prints the date of the rebuild for `{current_date}`; the help text recommends `{invoice_date}`.
- **SVG logos.** `Images::encode()` only knew raster types, so the Neonat SVG logo was silently dropped after the migration (1.x accepted it). Dompdf draws SVG itself: a local `.svg` file (checked by extension, since `wp_check_filetype()` does not know SVG on a site that has not allowed it) is embedded as `data:image/svg+xml`, up to 5 MB and only when it holds an `<svg` element. Pinned by `RenderingTest::test_svg_logo_is_embedded`.
- **Product table headers.** Uppercase labels in narrow columns broke inside a word ("REFEREN / CE") because the header allowed `word-wrap: break-word`. Headers now wrap between words only, with tighter letter spacing and the same small horizontal padding as the cells. The image column is merged into the product cell (thumbnail beside the name, the product column takes its width), so there is no empty header above the images.
- **Layout choices after 2.0.0.** The title band shows the document title only (the number is in the details block); the informational "excl. VAT" and VAT rows print just above the grand total (`Context::informational_before_grand()`, order only, never a value); the footer is a left-aligned block (free text, then the legal and contact lines) and `PdfEngine::draw_pagination()` writes "Page n / N" on the right, level with its last line. Issued invoices keep their archived PDF: only documents built afterwards get this layout.

## Issuing and archive

- **Order of operations** (`Documents\Issuer::issue()`, through the shared `Documents\Pipeline`): `Register::reserve()` first (unique key per order), then `Sequences::next()` immediately before `Register::assign()`. A second call for the same order (status hook plus email filter, or two requests) fails at `reserve()` and never touches the counter, so the sequence advances by exactly one.
- **A consumed but unrecorded number is never silent.** When `NumberFormat::build()` throws or `assign()` fails after `next()` for any reason other than a number already issued, the value is burned: logged and written as an order note naming the number and the sequence value, so the gap is auditable. A number already issued is not a gap (it is printed on another invoice): the next value is taken, at most 20 times, then "Invoice could not be numbered." is noted.
- **A number used by another document type is refused, never skipped.** The unique key `(type, number)` only separates numbers within one type, so an invoice and a credit note could both print the same number. Before `assign()`, `Pipeline::number()` asks `Register::number_exists_in_other_type()`: on a clash the row is released, the value is burned with a note and a log line, and the document is not numbered. Taking the next value instead would hit the same clash at every value (the formats share their prefix) and burn the counter: the fix is a distinct prefix per type. The note texts of each type live in `Documents\Notes` (the invoice texts are those of 2.0.1). Pinned by `IssuerTest::test_number_used_by_other_type_is_refused_not_skipped` (counter moved by exactly one) and `IssuerTest::test_invoice_order_notes_unchanged`.
- **Render from a fresh order.** The PDF is rendered from `wc_get_order()` after the number meta is saved, never from the `WC_Order` in hand: 1.x rendered a stale object and printed invoices without their number (bug C2).
- **A render failure keeps the number.** The "Invoice %s issued." note is written before rendering (a fatal error inside Dompdf still leaves it); a render or store failure adds its own note after. The row stays `issued` with no file; the first e-mail or download builds the PDF through `Issuer::restore()` and records it with `attach_file()`. A recorded file that is missing or damaged is only rebuilt by the explicit meta box button: into a **new** file recorded with `replace_file()`, the damaged file left in place.
- **Title.** `DocumentData::$title` wins when not empty, else the `content.invoice_title` setting (`credit_notes.title` for a credit note), else the translated "Invoice" ("Credit note"). `Issuer`, `Preview` and `DocumentData::credit_note()` pass `''`.
- **Rendering a credit note.** `Renderer::html()` / `pdf()` take the refunded order (parties, payment method, footer) and the refund's `CreditNoteStatementBuilder` statement; `DocumentData::credit_note()` reads the number and date of the credited invoice from the register (so an imported invoice keeps its legacy number), and returns null when the order has no issued invoice. `Context::build()` throws for a credit note without its statement or its reference: the order's amounts would be printed, or the mandatory "Credit note for invoice %1$s of %2$s" line (under the title band, no toggle) left out. The credit note number, its date and the refund date always print; the refund reason replaces the customer note (`credit_notes.reason_enabled`). The `lumia_factures_invoice_context` / `_html` filters run for both types and get the type as 4th argument.
- **Write-once files.** `Storage\Archive::store()` writes `Y/m/{number}-{16 hex}.pdf` with `fopen( 'xb' )`: an existing path is refused by the filesystem. Every folder (root, year, month) gets a `.htaccess` (Apache 2.4 and 2.2 rules) and an `index.php`; Nginx needs the rule from the README. `Archive::path()` only accepts `Y/m/*.pdf` resolving inside the root, so the Dompdf `fonts/` cache is never served as an invoice.
- **The status hook never throws.** `woocommerce_order_status_changed` is wrapped in `try/catch (Throwable)`: an invoice failure is logged and must not break the order status change.
- **After `assign()`, every step runs.** Order meta, render + store, order note and the `lumia_factures_invoice_issued` action are each wrapped and logged on failure: a third-party hook throwing from `$order->save()` must not skip the PDF or the note. Missing or different order meta is back-filled by the next `issue()` call on the issued document.
- **Stale reservations.** A `reserved` row with no number older than `Issuer::STALE_AFTER` (10 minutes) comes from a request that died between `reserve()` and `assign()`; `Pipeline::reserve()` deletes it with the guarded `Register::release_stale()` and reserves again once. A younger row is a call in progress and is left alone.
- **Guards before any render.** `Archive::ensure_root()` creates the root and `fonts/` with their `.htaccess` / `index.php`; `PdfEngine::options()` and `Archive::store()` both call it, so the Dompdf font cache never lands in an unprotected folder.

## Credit notes: issuing

`Documents\CreditNoteIssuer` issues one credit note per refund (register row `credit_note`, `order_id` = refund id, `parent_id` = order id) through the shared `Pipeline`, with its own series (`credit_notes` settings) and the notes of `Notes::credit_note()` on the order. The refund carries `_lumia_factures_credit_note_number` / `_date`; `_lumia_factures_credit_note_pending` holds why it was refused (see `refusal()`), written and logged once per reason.

- **Hook.** `woocommerce_order_refunded` only, the last step of `wc_create_refund()`: `woocommerce_create_refund` runs before the gateway is asked, and WooCommerce deletes the refund when the gateway refuses it. Pinned by `CreditNoteIssuerTest::test_gateway_refund_failure_leaves_no_credit_note`.
- **Pitfall: another request can see a refund the gateway is still deciding on.** `wc_create_refund()` saves the refund (amount, items, status) before it asks the gateway, and the gateway call can take seconds. A sweep spawned by a page load, a webhook that issues the invoice (`issue_pending()`), the "Issue credit note" button, the notice or `wp lumia-factures issue-credit-notes` reading the refund then would number it; when the gateway declines, `block_deletion()` keeps the refund for its credit note, and the order shows a refund that never happened with an immutable credit note for money never returned. Only `on_refunded()` and the refund e-mail (both after the gateway answered) call `issue()`; every other path calls `issue_deferred()`, which leaves alone, writing nothing, a refund created less than `Issuer::STALE_AFTER` seconds ago that carries neither number nor pending flag (`in_flight()`; `refusal()` reports `in_flight`). A pending flag is only ever written after the gateway answered, so a flagged refund is never in flight. Pinned by `test_gateway_refund_failure_leaves_no_credit_note_when_another_request_runs_during_the_gateway_call` and `test_refund_created_moments_ago_waits_for_deferred_paths_but_not_for_its_hook`.
- **Gate, in order.** Nothing refunded: nothing, never pending. Then no order (`no_order`), the import gate (`import`, `conflict`), a reused refund id (`reused_id`), the filter `lumia_factures_can_issue_credit_note` (veto only, after the import gate), and the invoice: issued, or issued first when the order was created since the option `lumia_factures_credit_notes_since` (recorded by the module's first boot, `Module::init()`, never moved), otherwise `no_invoice`. An order older than that gets no invoice by itself: its refunds are issued on demand.
- **Pitfall: a full refund changes the status before the hook.** `wc_create_refund()` saves the refund, moves the order to `refunded`, and only then fires `woocommerce_order_refunded`. With `refunded` as a trigger status, the invoice is issued during the status change; its `lumia_factures_invoice_issued` action (priority 20, `on_invoice_issued()` then `issue_pending()`) issues the credit note of the refund already saved, and the hook finds it. One invoice, one credit note, each counter moved once. Pinned by `test_full_refund_of_never_invoiced_order_with_refunded_trigger`. `issue_pending()` queries the refunds with `wc_get_orders()`: `WC_Order::get_refunds()` is cached and may predate a refund saved in the same request.
- **Pitfall: a refused deletion still fires the deletion hook.** `woocommerce_pre_delete_order_refund` refuses to delete a refund carrying a credit note (filter `lumia_factures_allow_credited_refund_deletion` to allow it; the row and the PDF stay, a note is written). The order screen deletes over AJAX, fires `woocommerce_refund_deleted` whatever `delete()` answered and ignores the response: `on_refund_deleted()` checks the refund is really gone (and notes it once, the data store firing `woocommerce_delete_order_refund` too), and the reason of a refusal is kept for the user and printed on the next admin page (`all_admin_notices`).
- **Pitfall: deleting an order for good deletes its refunds differently per storage.** HPOS (`OrdersTableDataStore::delete()`, `upshift_or_delete_child_orders()`) calls `$refund->delete( true )` on each refund before deleting the order rows, so the refunds go through `woocommerce_pre_delete_order_refund`; the legacy storage deletes them with `wp_delete_post()` (`WC_Post_Data::delete_post_data()`), which skips the filter. Refusing there left credited refunds in `wc_orders` without their order (WooCommerce Analytics kept counting them, and the manager got "cannot be deleted" right after deleting the order), also when HPOS empties the trash after `EMPTY_TRASH_DAYS`. `woocommerce_before_delete_order`, fired by both storages before anything is deleted, records the order (`on_order_deleting()`, which also logs the credit notes that stay issued); `block_deletion()` lets the refunds of that order through and `on_refund_deleted()` writes nothing on it, until `woocommerce_delete_order` (`on_order_deleted()`). The register rows and the PDFs stay. Pinned by `StorageModeTest::test_order_deleted_for_good_takes_its_credited_refunds_in_hpos_and_legacy` (run in both storages).
- **A refund id can come back.** MySQL may give a freed AUTO_INCREMENT value again, while the unique key `(type, order_id)` keeps the credit note of the deleted refund. `find_for()` only hands a row to a refund of the same order whose recorded number matches, and not when the order listed that refund id as deleted (`_lumia_factures_deleted_refunds`, written by `on_refund_deleted()`). An order deleted for good leaves no such list (`on_refund_deleted()` writes nothing then, and the meta goes with the order), and both ids may come back together: so a refund without the number is not handed an issued row whose issue date precedes the refund's creation by more than a minute (clocks of several web servers), since its own credit note is always issued after it. Such a refund is refused with `reused_id`, the old row untouched. Pinned by `test_reused_refund_id_with_other_parent_is_refused_never_returns_stale_row`, `test_refund_id_recorded_as_deleted_never_gets_the_old_credit_note` and `test_credit_note_issued_before_the_refund_was_created_is_not_its_own`.
- **Pitfall: the credit note start is recorded by a running module only.** `on_activate()` used to record `lumia_factures_credit_notes_since`, and activation runs whatever the requirements: a site activating 2.1 next to Facture PDF Lumia 1.x (to dry-run the import) recorded the activation time while 1.x kept handling the refunds for days. Once 1.x was gone, the sweep and the pending notice took those 1.x refunds as missed, and an order of that window got its invoice from a refund. Only `Module::init()` (which runs only when `Requirements::check()` passes) records it now, and `since()` reads it without recording. Pinned by `MigrationTest::test_activation_while_requirements_fail_records_no_credit_note_start`.
- **Sweep.** Daily cron `lumia_factures_credit_notes_sweep` (unscheduled on deactivation through the module's `cron` uninstall key), nothing while the import blocks issuing, 20 refunds at most: first those created since `lumia_factures_credit_notes_since` with neither number nor pending flag and a refunded amount above 0 (a refund of 0 is never flagged and would be retried forever), then the pending ones whose reason can lift without a hook (`import`, `conflict`, `vetoed`), so refunds waiting for something else never crowd out one the hook missed. `no_invoice` lifts when the invoice is issued, whose action issues the order's credit notes; `no_order` and `reused_id` never lift.
- **Pitfall: a sweep that restarts at the oldest refund starves.** Reading from the oldest refund every day, a window of 500 rows filled with refunds that never become issuable (pending for good, refunds of 0) hid every refund after them, and the 20 oldest pending refunds were the only ones ever retried: on a live shop the sweep silently stopped within months. Each part (missed, pending) now resumes after the creation date and id of the last refund it read (option `lumia_factures_credit_notes_sweep_cursor`, not autoloaded), reads to the newest refund, then wraps to the oldest one and stops at the cursor; once it has read everything the cursor is cleared. A creation date, not an id, because `wc_get_orders()` filters ids by list only. Pinned by `test_sweep_resumes_after_the_last_refund_read_and_starts_over` and `test_sweep_never_starves_behind_refunds_pending_for_good`.
- **Pitfall: `meta_query` does not exist on the legacy order storage.** `wc_get_orders()` passes `meta_query` to HPOS only; since WooCommerce 9.2 the posts storage raises a "doing it wrong" notice and drops it, so the query returned every refund. Only the single clause of the `meta_key` / `meta_compare` shortcut works in both storages: `pending_refund_ids()` uses it, and `sweep_ids()` queries the refunds without a number (by pages, 500 at most) and leaves out the refunds of 0 and the pending ones in PHP. Pinned by `StorageModeTest::test_pending_refunds_query_works_in_both_storages` (run in both storages).
- **Tests.** Test classes that only render credit notes or read statements remove the issuing listener in `set_up()` (WordPress restores the hooks after each test): `RenderingTest` records its own register rows for the refunds it renders.

## Credit notes: register, amounts, tools

- **Row model.** A credit note is a register row `type = 'credit_note'` whose `order_id` is the **refund** id and `parent_id` the refunded order (0 on an invoice). The unique keys stay `(type, order_id)` (one credit note per refund) and `(type, number)`; `Register::for_parent()` lists the credit notes of an order. The column comes with schema v2: the upgrade, its version check, the test that upgrades a separate v1 copy (any `ALTER` commits the test transaction) and the rollback to 2.0.1 are in [core.md](../core.md#database-schema).
- **Amounts.** `CreditNoteStatementBuilder` prints positive amounts and its summed rows equal `$refund->get_amount()` exactly. The refunded lines, shipping and fees become rows; no discount or coupon row (a refunded item already carries its discounted price). A gap between the refunded amount and its items of 1 or 2 minor units is a `rounding` row; above that it is one **signed** `adjustment` row "Other refunded amount" (a refund "by amount", or a manager who typed an amount above or below the lines), split over the order's VAT rates in proportion to their incl. VAT base (largest remainders), each share cut into excl. VAT and VAT; in excl. VAT display its VAT joins the VAT rows. Rates and labels always come from the order (see Pitfalls). Pinned by `CreditNoteStatementTest::test_amount_only_refund_two_rates_allocated_exactly`, `test_negative_adjustment_when_amount_below_line_sum`, `test_gap_of_one_or_two_minor_units_is_rounding_not_adjustment`, `test_sum_of_credit_notes_equals_total_refunded`.
- **Order screen** (`Admin\OrderTools`): the invoice box lists every refund with its credit note (number, date, download, "Rebuild missing PDF") or an "Issue credit note" button with the pending reason, and the register rows whose refund was deleted ("Refund #n deleted", still downloadable). Admin-post actions `lumia_factures_invoices_issue_credit_note`, `_restore_credit_note`, `_download_credit_note` and `_cancel_invoice`: nonce per refund (per order for the cancellation), `manage_woocommerce`, and the refund must belong to the posted order. The download reads the register row, so it works after the refund is gone (`OrderToolsTest::test_download_credit_note_serves_register_file_after_refund_deleted`). The orders list prints the credit note numbers under the invoice number.
- **Pending notice** (`Admin\CreditNoteNotice`, `all_admin_notices`, managers only): the refunds that should have a credit note and have none (created since `lumia_factures_credit_notes_since` and refunding something, or flagged pending), with a button (admin-post `lumia_factures_invoices_issue_pending_credit_notes`) that issues them. Older refunds are never counted: they are issued on demand.
- **Cancel the invoice** (`Documents\InvoiceCancellation`). An issued invoice is never changed or deleted, so an order cancelled after its invoice is credited: "Cancel invoice" (confirmation modal of the design system: no money is moved) records with `wc_create_refund()` a refund of everything not refunded yet, `refund_payment` and `restock_items` false, reason "Invoice cancelled"; its credit note follows through `woocommerce_order_refunded`. Refused (`refusal()`) while the import blocks issuing, without an issued invoice, for a paid order (a paid order is refunded, which goes through the gateway) and when nothing is left. The remaining items are sent only when they add up to the amount left; after a refund "by amount" the items no longer say what is left, so the cancellation goes by amount too. Two clicks are serialized by a per-order lock inserted with `INSERT IGNORE` (`add_option()` is not atomic, see the migration lock). Pinned by `InvoiceCancellationTest` (`test_cancel_twice_issues_one_credit_note`, `test_cancel_waits_while_another_request_holds_the_lock`, `test_cancel_after_amount_refund_goes_by_amount`).
- **WP-CLI** `wp lumia-factures issue-credit-notes [--order=<id>] [--since=<Y-m-d>] [--pending] [--dry-run]`: the refunds without a credit note number (or the pending ones), in id order, through `CreditNoteIssuer::issue()` (same gate, same pending flag). The dry run only reads (`refusal()`): it never reserves nor numbers. A real run is refused (`blocked`) while a requirement fails or the tables are missing; a dry run only needs WooCommerce. This is how the refunds made before 2.1 get their credit note, dated the day they are issued, with the refund date printed on the PDF.

## Settings screen

The whole plugin page (`templates/admin/invoices.php`). `includes/Modules/Invoices/settings-template.php` prints the module form (`lumia-factures-module-form`, the one the header "Save" button submits, `lumia_factures_tab=module_invoices`) with six design-system tabs (`data-lumia-tabs="invoices"`: General, Company, Numbering, Content, Design, Settings); each panel is `templates/admin/invoices/{tab}.php`, except Settings (`templates/admin/partials/plugin-settings.php`, global settings saved by the same form). Fields are rendered by `Admin\Fields` from the `Schema` definitions (name, min, max), so only labels and help texts are written by hand.

- **Tabs and the URL.** The design-system tabs remember the open tab in `sessionStorage`, not in the URL hash. `invoices.js` also opens the tab named by the hash (the raise redirect ends with `#numbering`).
- **Lists need a hidden empty entry.** An unchecked checkbox posts nothing, so a form with every box unchecked would post no `trigger_statuses` at all and keep the old value. `Fields::checklist()` prints `<input type="hidden" name="...[]" value="">` first; the Schema drops empty strings and saves `[]`.
- **Forms cannot nest.** The "Raise counter" forms are standalone `<form>` elements printed after the module form; the inputs and buttons inside the counters table point to them with the HTML5 `form="lumia-factures-raise-{n}"` attribute. Those inputs still sit inside the module form in the DOM, so their `input`/`change` events would mark the settings as unsaved: `invoices.js` stops them at the table.
- **Raising a counter** (`Admin\Counters`, admin-post `lumia_factures_invoices_raise_counter`): `raise_for()` only accepts a key that already exists (the client cannot create counters) and delegates to `Sequences::raise()`, which never lowers a value. Notice codes `counter_raised` / `counter_not_raised` go through the `lumia_factures_admin_notices` filter and the `lumia_factures_notice` query args.
- **Policy changes carry the counter.** Saving a new format or reset policy raises the counter of the new policy's key to the old key's value (see Pitfalls, R38). A refused format also reverts `reset_enabled` and `reset_period` (`SettingsSchemaTest::test_invalid_format_also_reverts_the_reset_policy`). `Module::carry_counter()` runs once per numbered type (`Schema::NUMBERED`), on that type's own keys (`SettingsSchemaTest::test_carry_counter_runs_per_type`).
- **Credit note settings** (group `credit_notes`, spread over the General, Numbering and Content tabs): their own numbering policy (`format` `AV-{year}-{number:5}`, `start_number`, `reset_enabled`, `reset_period`, counters `credit_note`, `credit_note_{Y}`, `credit_note_{Y}_{m}`), `title`, `reason_enabled` and `email_attachments`. There is no `enabled` key: credit notes cannot be turned off. `Schema::NUMBERED` maps each numbered type to the group of its policy; each policy is validated on its own and a refused one reverts alone. Settings saved by 2.0 have no `credit_notes` group: `Module::settings()` reads it from the defaults, no migration needed.
- **Distinct prefixes.** The register's unique key `(type, number)` only separates numbers within a type, and `Pipeline::number()` refuses (and burns) a number already used by another type. To keep that from ever happening, `Schema::sanitize()` requires `NumberFormat::prefixes_differ()`: the credit note prefix (text before the first tag) is not empty; behind a literal invoice prefix neither prefix starts the other (`FA-` / `FA-AV-` refused, `FA-` / `FAV-` accepted); when the invoice format starts with a tag (Neonat keeps `{year}{month}{number:6}`) the credit note prefix must not start with a digit (`2026-` would meet `{year}-{number:5}`). The comparison folds case and accents like the register collation. A refused pair reverts the credit note policy, then the invoice policy too when the conflict came from the invoice format alone. Pinned by `SettingsSchemaTest::test_credit_note_format_must_differ_from_invoice_format` and `test_credit_note_prefix_needs_non_digit_when_invoice_format_starts_with_tag`.
- **Pitfall: the two formats being saved are not the whole story.** Checking only the posted pair let an admin swap the prefixes (invoices `AV-`, credit notes `FA-`) in one save. `Module::carry_counter()` keeps both series going, so the next credit note printed `FA-2026-00011`, the number of an issued invoice: `Pipeline::number()` refused and burned value after value until the counter passed the last invoice, and no credit note could be issued meanwhile. `Schema::sanitize()` (`separate_series()`) therefore also checks each type whose prefix changes (`prefix_is_free()`): the new prefix must differ from the other type's **current** format, and no number of the other type in the register may start the way the new numbers start (`Register::number_starts_with()`, a `LIKE` that follows the register collation; for an invoice format starting with a tag, any digit, see `NumberFormat::number_starts()`). The register catches the swap done in two saves (`FA-` to `FAC-`, then credit notes `FA-`). A refused type reverts on its own, with the error "A number format cannot take a prefix that the other document type uses or has already printed". An unchanged prefix is never looked up (the current settings are assumed valid). Pinned by `SettingsSchemaTest::test_prefix_cannot_take_numbers_of_the_other_type`.
- **Refund emails carry the credit note, never the invoice.** `Schema::email_options()` takes a scope: the invoice list (`general.email_attachments`, scope `invoice`) never offers `customer_refunded_order`, the credit note list (scope `refund`) offers it only. WooCommerce renames the email `customer_partially_refunded_order` while it sends a partial refund; both ids are in `Schema::REFUND_EMAILS`, and `Emails\Attachments` ignores them for the invoice even when a 2.0 save stored one in the invoice list.
- **Pitfall: the refund email leaves before `woocommerce_order_refunded`.** WooCommerce sends it from `woocommerce_order_partially_refunded` / `woocommerce_order_fully_refunded` (after the gateway refunded the payment, before the issuing hook). `Emails\Attachments` therefore calls `CreditNoteIssuer::issue()` itself (idempotent: the hook, a deferred or a resent email find the same credit note) for the refund in `$email->refund`, only when the normalized id is in `credit_notes.email_attachments`. No refund object, a refund of another order, a WooCommerce email preview (`woocommerce_is_email_preview`) or an order / refund that is not the stored one (order key, parent id): nothing is issued or attached. Pinned by `EmailAttachmentsTest::test_email_issues_credit_note_before_woocommerce_order_refunded_and_hook_reuses_it`.
- **Pitfall: the refund email object keeps the partial id.** `WC_Email_Customer_Refunded_Order::trigger()` sets `$this->id` on the mailer's single instance, which keeps `customer_partially_refunded_order` for the rest of the request (or PHPUnit process) after a partial refund email. Read as is, `Schema::email_options( 'refund' )` returned only the partial id, so a save dropped the stored `customer_refunded_order` and the General tab offered the partial id. Every id read from an email object goes through `Emails\EmailIds::normalize()` (partial id to `customer_refunded_order`), deduplicated, in `email_options()` and in the General tab titles. Pinned by `SettingsScreenTest::test_refund_email_keeps_its_id_after_a_partial_refund_email`.
- **Order screen notices** (`OrderTools::render_notice()`) are printed on `all_admin_notices`, not `admin_notices`, which lumia-tools moves into its drawer.
- **Schema errors** (`lumia_factures_invoices_errors` transient, 60 s) are printed as a `lumia-notice--error` above the panels and deleted when read. `SaveHandler` still redirects with the generic "Settings saved" toast: the other settings were saved, only the numbering fields were refused.
- **Live number samples.** One per `[data-lumia-factures-sample="{type}"]` (invoice and credit note), computed in `invoices.js` from `lumiaFacturesAdmin.invoices` (today's date in the site timezone, order `14243`, customer `27`, the counters by key, the known tags, and `documents`: the settings group of each type). It mirrors `NumberFormat::preview()` and `Sequences::key()`; there is no AJAX. The counters table names the document type of each key (`Counters::document_type()`).
- **Logo.** `wp_enqueue_media()` on the plugin screen (`Module::enqueue_media()`), script dependency `media-editor`. The value is the attachment id (`company[logo_id]`).
- **Design tab ("Appearance").** Themes first: `Admin\Themes::all()` is the single source of the palettes (the first one is the Schema default). A theme button only fills the color fields through `invoices.js`; nothing but the colors is stored, and the button whose colors all match the form shows as pressed. `SettingsScreenTest::test_themes_are_complete_and_keep_the_header_text_readable` checks each palette covers every color key and keeps the header text at WCAG AA contrast on the title band and the table header (`color_thead_text` is printed on both `color_primary` and `color_thead_bg`). Then the primary color, the other colors in a collapsible "Advanced colors" block, typography and layout.
- **Color fields.** `Fields::color()` prints the native swatch (the posted value) and a hex text box **without a name** kept in sync by `invoices.js`: typing a valid code (`#abc` or `#aabbcc`) sets the swatch, picking a color rewrites the code (not while the code box has the focus). Enter in the code box is swallowed: it would submit the whole form.
- **No secondary color.** `design.color_secondary` existed until 2.0.0 but the PDF template never printed it; it was removed from the Schema. A stored value is ignored; the legacy import lists it in `LegacySettings::REMOVED_DEFAULTS`, so only a customized value gets a note.

## Live preview

`Admin\Preview` (AJAX `wp_ajax_lumia_factures_invoices_preview`, nonce `lumia_factures_admin_nonce`, `manage_woocommerce`) renders the **unsaved** form against a real order: the given `order_id` (a refund or an unknown id is refused), else the latest order that is not a `checkout-draft` (the block checkout keeps one per cart, an empty order the shop never received), else the demo order (`Admin\DemoOrder`) when the shop has none. The response carries `demo`, and the pane then shows "No order yet: demo order built from your products and shop address, without order number. Nothing is saved."

- **Input.** `invoices.js` posts a `FormData` of the whole module form (nested `lumia_factures_module_settings[group][key]`, same shape as a save) with `action`, `nonce` and `order_id` overridden. Never post the form's own `action`: it is the save action.
- **No side effect.** The settings go through `Schema::sanitize()` against the stored ones and are never saved. The preview never calls `Issuer`, `Register`, `Sequences::next()` or `Archive::store()`; the number is `NumberFormat::preview()` of the next counter value, read with `Sequences::current()`. `DocumentData::$preview` is true, which prints the translated "Preview" watermark (`.lf-watermark`, `position: fixed`, rotated) in `templates/pdf/invoice.php`. The Dompdf font cache still writes under the archive root `fonts/`, which is not an invoice file.
- **Pane.** `templates/admin/invoices/preview.php`, a column next to the fields of the tabs that change the PDF (`data-lumia-factures-preview-tabs="company content design"`), hidden on the others; under 1100 px it goes below the fields. Any `input`/`change` in the form marks the preview stale; while the pane shows, a change is rendered after a 600 ms debounce, otherwise when the pane shows again. A request counter keeps only the latest response. The order field has no `name`, so it is never saved and never marks the form as unsaved; Enter in it refreshes instead of submitting the form.
- **Drawing.** pdf.js (`assets/vendor/pdfjs/`, see its README for the version and the update steps) draws every page on a canvas, white sheets on a grey background, fitted to the pane width times the zoom (50 % to 300 %, the middle button fits again); a resize redraws. The pages are drawn off screen and swapped in at once, so typing does not flicker. pdf.js is loaded with `import()` on first use only (the files are ES modules named `.js`, because some servers do not serve `.mjs` as JavaScript) with a module worker.
- **Fallback.** If pdf.js cannot load or read the file, the PDF goes into an `<iframe>` (Blob URL, the browser's own viewer) and a console warning says why.
- **Pitfall: destroy the loading task.** In pdf.js 6 the document proxy has no `destroy()`: the `PDFDocumentLoadingTask` owns the document and its worker resources. Calling `doc.destroy()` threw on the second render, which silently sent every later preview to the fallback viewer.
- **Demo order: a `WC_Order` that must never write.** `DemoOrder` extends `WC_Order` with id 0, built in memory from the shop's own data: up to the three latest published products with a price (a variable product gives its first published priced variation), quantities 1, 2, 1, else one "Sample product" line at 10; the shop base address for "Sample customer" / "Sample recipient" (`customer@example.com`, no phone); the first enabled payment method; the shop currency. Every write method is a no-op (`save()` returns 0, `save_meta_data()`, `delete()`, `add_order_note()`, `update_status()`, `payment_complete()`), and `add_product()` builds the item without `$item->save()`. Pinned by `DemoOrderTest::test_build_writes_nothing` (orders, items, meta, comments, counters and register unchanged, in both storages) and `test_write_methods_are_noops`.
- **Pitfall: order 0 has rows.** WooCommerce reads the items, refunds and meta of an order by id; for id 0 it would read the orphan items some plugins leave with `order_id = 0`. `DemoOrder` sets every item group up front (`$this->items`, so `read_items()` never runs) and answers no refund. Pinned by `test_ignores_orphan_items_of_order_zero`.
- **Pitfall: `calculate_totals()` saves.** It saves the order and its items. The demo computes its taxes in minor units as WooCommerce stores them (`WC_Tax::find_rates()` at the shop base address, per product tax status and class, rounded per rate, compound rates included, one `WC_Order_Item_Tax` per rate) and sets the total to their exact sum, so the statement adds up without a rounding row in both display modes (`test_demo_adds_up_incl_and_excl`, `test_compound_rate_adds_up`). Shipping (5 excl. VAT) only when shipping is enabled and a product ships, its tax class resolved as `WC_Tax::get_shipping_tax_rates()` does, `inherit` included (`test_shipping_inherit_class`).
- **Pitfall: the order number filter.** `get_order_number()` returns `''` without running `woocommerce_order_number`: a sequential numbering plugin would look up order 0. The preview prints the next sample invoice number as for a real order (`test_order_number_is_empty_and_unfiltered`, `PreviewTest::test_demo_preview_number_is_the_next_sample`).
- **Pitfall: third-party hooks meet an order without id.** The demo is rendered inside a `try/catch (Throwable)`: a hook that cannot handle it becomes the preview error `lumia_factures_preview_failed`, never a fatal error of the settings screen (`PreviewTest::test_demo_preview_survives_throwing_hook`).

## Legacy migration: lifecycle and issuing gate

`Migration\Migration` runs `Migration\Importer` by itself and tells the issuer when numbering may start.

- **State** (option `lumia_factures_migration`): `none`, `pending`, `running`, `done`, `done_with_conflicts`, `failed`, with `started_at`, `finished_at`, the last `report` (`Report::to_array()`) and the last `error`. A site without legacy data stays `none` and the option is never written.
- **Activation only marks it pending.** `Module::on_activate()` forgets the cached "no legacy data" answer and, when `Requirements::check()` is clean, sets `pending` (when `LegacySource::has_data()` and the status is `none`). It never runs the import: inside `activate_plugin()` the plugin has not booted, no module is registered and the text domain is not loaded.
- **When it runs by itself.** `Module::init()` calls `Migration::boot()`, which plans (`prepare()`) and runs (`maybe_run()`) only when `may_auto_run()` allows it: an admin page (not AJAX, not the retry action) opened by a user with `manage_woocommerce`, a WP cron request, or under WP-CLI only `wp cron event run ...` (`cli_may_auto_run()`: the cron container drives WordPress that way). Never on a front-end request, never for an anonymous visitor (`admin-post.php` fires `init` before authentication), never for another WP-CLI command: `wp lumia-factures migrate` runs it explicitly, and its dry run must report on the data as it is.
- **Back-off.** A `failed` import is retried automatically only 15 minutes (`STALE_AFTER`) after the failure, so a failure that repeats does not cost every admin request a full attempt. A manual retry (the notice button, `wp lumia-factures migrate`) passes `maybe_run( true )` and does not wait.
- **Lock heartbeat.** Each importer batch fires `lumia_factures_legacy_import_batch_done`; during a real run `Migration::heartbeat()` refreshes the lock (compare-and-swap on the value this run holds) and the state's `started_at`, so a run longer than 15 minutes is never taken for a dead one and taken over.
- **Negative cache of `has_data()`.** A site without legacy data caches the answer 12 hours (transient `lumia_factures_no_legacy_data`), so `blocks_issuing()` does not query the order meta on every issue. It is cleared by the plugin activation, the "Run the import now" button and every `wp lumia-factures migrate` (which looks again with `LegacySource::has_data()`). Legacy data that appears later (a database restored over the site) is therefore seen at the latest 12 hours later, or at once through one of these.
- **Gate.** `Issuer::can_issue()` applies `Issuer::gated()` after the `lumia_factures_can_issue` filter, so a third-party filter cannot bypass it. `Issuer::gate_reason()` returns `import` (the import is not finished, `Migration::blocks_issuing()`), `conflict` (the order carries `_fpl_invoice_number` without an issued register row: it stays refused until handled by hand) or `''`. A refusal writes one order note per reason: "Invoice not issued: the Facture PDF Lumia data is being imported." or the conflict note. The flag `_lumia_factures_gate_noted` holds the last reason noted (not a boolean), so an order first refused during the import and then found in conflict gets both notes, each once; `sync_meta()` clears it once the order is invoiced. The order meta box reads `gate_reason()` (which never writes) and words a conflict as a conflict, so viewing an order never writes a note.
- **Retry.** While issuing is blocked, `Admin\MigrationNotice` prints a notice on `all_admin_notices` (managers only) with the status, the counts and a "Run the import now" button (admin-post `lumia_factures_invoices_migrate`, nonce + `manage_woocommerce`).
- **Conflict warning.** Once the import is done with conflicts, `MigrationNotice::render_conflicts()` prints a warning on `all_admin_notices` (managers only) with the number of skipped invoices and, for the first 20, a link to the order edit screen (`OrderUtil::get_order_admin_edit_url()`, HPOS or posts), the legacy number and the reason. "Dismiss" posts to admin-post `lumia_factures_invoices_dismiss_conflicts` (nonce + `manage_woocommerce`) and stores the `finished_at` of the run in the user meta `lumia_factures_conflicts_dismissed`: each manager dismisses it for their own account, and a later run that reports conflicts shows it again.
- **WP-CLI.** `wp lumia-factures migrate [--dry-run] [--force]` and `wp lumia-factures migration-status`. The logic is in `Cli\Command::migrate_data()` / `status_rows()`, which return data (tested without WP-CLI). The command is registered by `Core\Plugin` whatever the requirements, so the dry run and the status work while the legacy plugin is still active (the modules have not started: when our tables do not exist yet, `Importer` reads an empty register and counters at 0). A real `migrate` is refused (`blocked`) while any requirement fails; a dry run only needs WooCommerce. A dry run never takes the lock nor changes the state. The status lists what blocks the plugin, the current counters and the highest legacy sequence per key (legacy meta and legacy table).
- **Escape hatch.** A conflict or a failed run is fixed by hand, then `wp lumia-factures migrate --force` runs the import again: it imports nothing twice, completes what is missing and never lowers a counter. A failure that repeats with the same error (deterministic: a corrupt legacy row, a third-party hook throwing on save) does not go away by retrying: read the error in `migration-status` and the PHP error log (`[lumia-factures]` lines), fix the data or deactivate the faulty plugin, then run `--force`. Issuing stays blocked meanwhile; the legacy data is never modified, so nothing is lost by waiting.

Pitfalls:

- **`add_option()` is not a lock.** It reads the option, then inserts with `ON DUPLICATE KEY UPDATE`: two requests can both "add" it. The run lock (`lumia_factures_migration_lock`, value `{timestamp}-{token}`) is inserted with a raw `INSERT IGNORE` (one affected row = ours), a lock older than 15 minutes is taken over with a compare-and-swap `UPDATE ... WHERE option_value = <old>`, and it is released in a `finally` only when it still holds our token. The object cache entry is dropped after each raw write.
- **A run killed by a fatal error** (memory, time) never reaches the `finally`: the lock and the `running` state stay. After 15 minutes `state()` reports `failed`, the lock is stale, and the next admin/cron request runs again; the importer resumes where it stopped.
- **The execution time is only raised, never lowered**: `set_time_limit( 300 )` only when a limit below 300 s applies (an unlimited CLI run, the PHPUnit process included, keeps no limit).
- **The command must not depend on the module.** It was first registered in `Module::init()`, which never runs while `Requirements::check()` fails: with the legacy plugin still active (`legacy_active`) the runbook's dry run answered "not a registered command". The tables may be missing at that point too, hence `Installer::tables_exist()` (test seam `lumia_factures_tables_exist`: a test cannot drop a table).
- **A legacy number can appear during the run.** An in-flight request of the legacy plugin may number an order behind the import cursor after the counters-first pass. The final counter pass reads `LegacySource::max_sequences()` again, so such a number raises the counter, but its invoice is imported only by a later `wp lumia-factures migrate --force`. The order stays gated (`conflict`) until then.
- **DDL commits the test transaction.** `Installer::install()` (dbDelta) can issue an `ALTER TABLE`, which is not rewritten to a temporary table and commits the transaction the WordPress test suite wraps each test in: the legacy fixtures created before it leaked into every later test (a committed order made `has_data()` true everywhere). `MigrationTest` runs `on_activate()` with `dbdelta_queries` emptied.

## Legacy import: what is copied

`Migration\Importer` reads the Facture PDF Lumia data and never writes to it: the options `fpl_*`, the table `{prefix}fpl_sequences`, the order meta `_fpl_invoice_*` and the files under `uploads/facture-pdf-lumia/` stay as a fallback.

- **Settings** (`fpl_settings` -> `lumia_factures_module_invoices`) through `LegacySettings::map()`, only when the user never saved settings here (an option still equal to the defaults counts as never saved). A whole group missing from the option (a group added by a later version, such as `credit_notes` in 2.1) is read from the current defaults before the comparison (`Importer::left_at_defaults()`): otherwise the 2.0 defaults stored by the activator, updated to 2.1 before the import ran, would count as user settings and the legacy settings would be skipped. Pinned by `ImporterTest::test_settings_left_at_defaults_of_an_older_version_are_replaced`. Mapping notes go to the report. 1.x had no credit notes: a legacy invoice format that takes the default credit note prefix (`A{year}{month}{number:5}` and `AV-`) would make `Schema::sanitize()` revert the legacy invoice policy to the defaults, changing the format mid-series. `Importer::sanitize_settings()` keeps it: it tries the credit note formats `AVOIR-{year}-{number:5}` then `CN-{year}-{number:5}` (given as the current format, so never compared to the default invoice format no document was issued with), keeps the first with no error, and adds a note naming it. Pinned by `ImporterTest::test_legacy_invoice_format_clashing_with_credit_note_prefix_is_kept`.
- **Invoices.** One register row per order carrying `_fpl_invoice_number`, with its number, sequence key, sequence and date. The date falls back to the PDF generation time, then to the order creation date (a report note says so). The new order meta `_lumia_factures_invoice_number` / `_date`, the note flag and an order note are written with a single `$order->save()`, so the order hooks and webhooks fire once per imported order.
- **PDFs.** A legacy PDF still on disk is validated (a real PDF, inside the legacy folder), copied into the archive and recorded with its checksum. An invoice without a file, or with a damaged one, is imported with `file = NULL`: it is built on first need with its original number and date (admin download, customer download, e-mail attachment).
- **Counters.** Each key is raised to `max(legacy table value, highest imported sequence)`, never lowered. They are raised **before** the invoices are imported, so an interruption cannot leave a counter behind a legacy number, and again at the end with the legacy meta read once more. `LegacySource` ignores values that are not plain non-negative integers (a negative or overflowing value in the legacy data would otherwise corrupt a counter).
- **Conflicts.** A number already in the register, or an order that already has another invoice, is reported and skipped; the run ends `done_with_conflicts`.
- **Bricks.** Nothing to do: the Bricks module is locked, so the legacy `{fpl_invoice_*}` tags of a template keep rendering (see [bricks.md](bricks.md)).
- **Dry run.** Same code, every write skipped: its report equals the one a real run gives.

## Customer download, shortcode and legacy URLs

`Front\CustomerDownload` answers `init` priority 20 on `?lumia_factures_invoice=<order id>[&key=<order key>][&inline=0]` and on the links of the old plugin (`?fpl_download=1&order=<id>[&document=invoice][&key=...][&inline=1]`), so the links already sent in e-mails and thank-you pages keep working. Only `fpl_download=1` is handled, like the old plugin: any other value is not ours and the request goes on.

- **Access** (`can_access()`): a user with `manage_woocommerce`, the order's customer, or the holder of the order key (`hash_equals`). Filter `lumia_factures_can_access_invoice`. `url()` adds the key unless the visitor gets in without it (manager or owner): a guest, or a logged-in user who is not the owner, keeps it.
- **Credit notes** (`?lumia_factures_credit_note=<refund id>[&key=<key of the refunded order>][&inline=0]`): the register row `('credit_note', id)` must be issued, and access is decided on its `parent_id` order (`can_access( $order, $key, 'credit_note' )`), so the credit note stays reachable after its refund was deleted. Precedence: the invoice var, then the credit note var, then `fpl_download` (invoices only, `document=credit_note` is a 404); a request is never resolved against two documents. `Front\Availability::is_available()` (issued and either a verified archive or a NULL file the endpoint can build) is the single answer for every customer link (Bricks tags included).
- **One answer for every refusal**: a 404 "Document not found." (invoices and credit notes alike) for an unknown order, a wrong key, another customer, an order with no issued invoice, a rate-limited build or a damaged archive. Nothing tells whether an order exists.
- **Disposition.** The new URL displays the PDF in the browser (`inline=0` asks for an attachment); the old URL downloads it unless `inline=1`, like the old plugin did.
- **Same rule as the admin download (R41).** Only a register `file` that is NULL is built on first need (`Issuer::restore()`); a recorded file that is missing or damaged is a 404 for a visitor and is rebuilt explicitly by a manager from the order.
- **Rate limit.** 10 builds per 60 seconds per user (or IP), transient `lumia_factures_rate_<md5>`, counted only when a never-built PDF must be generated: serving an archived file is never limited. The window starts at the first build.
- **Shortcode** `[lumia_factures_invoice order_id="" label="" class="" inline="0"]` and the alias `[facture_pdf_lumia]` (same attributes; the alias keeps the class `fpl-download-button` by default). It renders a link only when an issued invoice exists and `can_access()` is true, never a dead button. Without `order_id` the order comes from the WooCommerce page (`OrderContext`).
- **Documents shortcode** `[lumia_factures_documents order_id=""]`: the documents block of the order pages (`CustomerLinks::documents_html()`, template `order-documents.php`), invoice then credit notes, each kept only when `can_access()` lets the visitor in for its type, with the key of the page. An explicit `order_id` only names the order to check, it never bypasses the access check; a refund id lists nothing. Placement `shortcode` of `lumia_factures_show_customer_links` (no setting). The Bricks tag `{lumia_factures_documents}` renders the same HTML (`Shortcode::documents()`).

Pitfalls:

- **A builder hands over the wrong post.** Bricks gives the `WP_Post` of the "My account" page even on the "View order" endpoint, and under HPOS that post ID can equal another order's id. `OrderContext::resolve()` therefore reads the endpoint first (query vars `view-order` / `order-received`, then the configured endpoint in the request URI) and only then the subject.
- **Access is checked for every tag and the shortcode**, never inferred from the context: a page that renders them for the wrong order shows nothing.

## Customer access

Since 2.1 the customer finds the order's documents (the invoice, then the credit notes in the order they were issued) in the e-mails, in My Account and on the thank-you page, besides the shortcodes and the Bricks tags. Every surface prints `Front\DocumentList::for_order()`, which lists only what a link would serve (`Availability::is_available()`).

- **Settings** (group `customer`, section "Customer access" of the General tab): `account_orders` (an "Invoice" button in the My Account orders list, never a credit note), `order_details` (a "Documents" block after the order table) and `email_links` (the customer e-mails that carry the links; default processing, completed, customer invoice and refund). Each placement then goes through the filter `lumia_factures_show_customer_links( $show, $placement, $order )`, placement `account_orders`, `order_details`, `email` or `shortcode` (the shortcode and the Bricks tag have no setting).
- **Access filter.** `CustomerDownload::can_access( $order, $key, $type )` decides for both types on the order (the refunded order for a credit note): `lumia_factures_can_access_invoice` still runs for invoices only (2.0 compatibility), then `lumia_factures_can_access_document( $can, $order, $key, $type )` for every document.
- **Templates.** `order-documents.php` (pages, shortcode, Bricks) and `emails/order-documents.php` / `emails/plain/order-documents.php` load through `wc_get_template()` from `templates/front/` and can be overridden in the theme under `lumia-factures/`. Each is rendered into a buffer: a template that fails half way prints nothing, and the buffers WooCommerce opened are left alone.

Pitfalls:

- **Nothing is issued from a page.** `DocumentList`, `CustomerLinks`, the shortcodes and the Bricks tags only read: no `Issuer::issue()`, no `Issuer::can_issue()` (which writes the gate note), no `save()`. A page view (a bot, a prefetch, a customer reloading the thank-you page) must never number an order. So the thank-you page shows nothing until the invoice exists: with a payment gateway that confirms later, the invoice comes with the status change. Pinned by `DocumentListTest::test_never_writes` (notes, meta, modification date and register unchanged, also for an order the import gate blocks) and `CustomerLinksTest::test_render_never_issues`.
- **An order id can come back too.** An order deleted for good keeps its credit notes (register rows with `parent_id` = its id; `on_order_deleting()` lets its refunds go), and MySQL may give the freed id to a new order of another customer. Matching the rows on `parent_id` alone listed the old credit notes for the new order and served their PDF with its key. `on_order_deleting()` therefore records the deletion time of an order that has credit notes (option `lumia_factures_deleted_orders`, not autoloaded), and `CreditNoteIssuer::belongs_to( $doc, $order )`, checked by `DocumentList` (so the pages, shortcodes, Bricks tags and e-mails) and `CustomerDownload`, refuses a row issued before that deletion when the live order was created after it. A live order created before it is the one whose deletion did not complete: it keeps its credit notes. The invoice row of a reused order id has the same weakness (it predates 2.1) and is not covered. Pinned by `DocumentListTest::test_order_given_the_id_of_a_deleted_order_never_lists_its_credit_notes`, `test_order_whose_deletion_failed_keeps_its_credit_notes`, `CustomerDownloadTest::test_credit_note_of_a_deleted_order_is_404_for_the_order_given_its_id` and `StorageModeTest::test_order_deleted_for_good_takes_its_credited_refunds_in_hpos_and_legacy`.
- **E-mails do issue, idempotently.** WooCommerce renders the body (`woocommerce_email_order_meta`, priority 20, 4 arguments) before it asks for the attachments, and the processing e-mail may leave before `woocommerce_order_status_changed` reaches the issuer. `Emails\EmailLinks` therefore calls `Issuer::issue()` (and, for the refund e-mail, `CreditNoteIssuer::issue()` on `$email->refund`) like `Attachments` does: both find the same number, and the hooks after them too. Nothing is printed or issued for an e-mail sent to the shop, without its `WC_Email` argument, or for a refund passed as the order. Any failure is logged and the e-mail always leaves. Pinned by `EmailLinksTest::test_processing_email_issues_and_links_invoice_before_status_changed`, `test_email_links_idempotent_with_attachments`, `test_issue_failure_never_breaks_email`.
- **The WooCommerce e-mail preview (WC 9.6+) uses a dummy order that may carry a real id.** Issuing from it would number the real order with the dummy's data. Before any issue, both `EmailLinks` and `Attachments` check `woocommerce_is_email_preview` and that the order is the stored one (same id **and** same order key in the database; for a refund, same id and same parent). Pinned by `EmailLinksTest::test_preview_dummy_order_never_issues` and `test_order_key_mismatch_with_db_never_issues`.
- **The key in an e-mail link is a permanent token.** E-mail links always carry the order key (`with_key` true), whoever triggered the e-mail (a manager resending it from the order screen too: the link is read by the customer, not by the manager). The key never expires: anyone holding the e-mail opens the documents, as with the WooCommerce order-received link. There is no revocation short of changing the order key; the pages never put the key in a link for a visitor who gets in without it (manager or owner). Pinned by `EmailLinksTest::test_email_link_carries_key_when_triggered_by_admin`.
- **The partial refund e-mail keeps its partial id.** WooCommerce sends `customer_partially_refunded_order` for a partial refund: `EmailIds::normalize()` maps it to `customer_refunded_order` before the setting is read, in `EmailLinks` as in `Attachments`, so one checkbox covers both. The refund e-mail lists the invoice and the credit note of **its** refund only (`DocumentList::for_order( ..., $only_refund_id )`), the same credit note `Attachments` attaches. Pinned by `EmailLinksTest::test_partial_refund_email_lists_only_that_refund_credit_note`.
- **One hook for every order page.** `woocommerce_order_details_after_order_table` is fired by the classic "View order" page, the classic thank-you page and the Order Confirmation **Totals** block (`OrderConfirmation\Totals`). `woocommerce_thankyou` is not hooked: on the classic thank-you page the block would come twice. The block is printed once per order and request, only for the order of the current endpoint (`OrderContext::current_order_id()`: the order tracking page prints the same table without an endpoint and gets nothing), and only to a visitor `can_access()` lets in with the key of the page. Pinned by `CustomerLinksTest::test_no_thankyou_hook_registered`, `test_details_block_rendered_once_per_order`, `test_details_block_hidden_on_order_tracking_page`.
- **Block themes need the Totals block.** In a block theme the Order Confirmation template fires the hook only from the `woocommerce/order-confirmation-totals` block: a template without it shows no documents. Use the `[lumia_factures_documents]` shortcode (or the Bricks tag) there. Pinned by `CustomerLinksTest::test_block_order_confirmation_totals_renders_documents`.
- **Page links are off after an update.** A shop that already showed its documents (Neonat, through Bricks) would get two lists the day of the update. `Settings\Upgrader::maybe_upgrade()` (marker option `lumia_factures_invoices_settings_version`, runs once) turns `account_orders` and `order_details` off on an existing installation (a recorded DB version, a register row, a migration state other than `none`, or 1.x data), keeps a value already stored and leaves `email_links` on; a fresh installation keeps every link on. It runs **before** `Installer` (in `on_activate()` and in `Module::init()`): the installer records the DB version, which would make every fresh site look like an existing one. It writes the settings option only. Pinned by `SettingsUpgraderTest` (`test_upgrade_runs_before_installer_in_on_activate`, `test_upgrade_never_touches_register_sequences_or_archive`).
- **The import must ignore that group.** The upgrader writes the `customer` group before the 1.x import runs, so the stored settings no longer equal the defaults and the legacy settings would be skipped as "saved by the user". `Importer` compares the settings without the `customer` group and puts the stored group back over the imported settings. Pinned by `ImporterTest::test_settings_imported_despite_upgrader_customer_group` and `test_import_keeps_stored_customer_group`.
